# CMP 170HX (GA100 / CUDA sm_80)

The default Docker build includes native `sm_80` code for both QEngine libraries. On GA100, QEngine uses its Ampere Tensor Core and asynchronous-copy kernels. The host driver must expose the card as a CUDA device. Check the card model, compute capability and actual memory before selecting the model and devices.

```sh
nvidia-smi --query-gpu=index,name,compute_cap,memory.total --format=csv
cmake -S . -B build -G Ninja -DCMAKE_CUDA_ARCHITECTURES=80 -DCMAKE_BUILD_TYPE=Release
cmake --build build --target qengine qflash cuda_compat_unit
ctest --test-dir build -R '^cuda_compat_unit$' --output-on-failure
```

For a text-only image targeting CMP 170HX alone:

```sh
docker build -t qengine:cmp170 --build-arg CUDA_ARCHS=80 --build-arg VISION=0 .
```

Select the actual cards with `QE_DEVICES` for a source run or `QE_GPUS` for Docker. The default communication mode probes peer access and exchange integrity before picking a transport. With `FLASH_BOX_REPORT=1`, Flash-Next logs the code target, memory and PCIe link of each selected GPU. Check for `native sm_80` in that report. See the [link probe documentation](../README.md#link-probe-and-flash_comm--qe_comm) for the available routes.

Model capacity, long-context behavior and performance depend on the usable VRAM and interconnect. Verify those on the target cards with the model and device count you intend to serve.
